## 1. 핵심 결과

**점검 범위에서 프로젝트의 실제 API 키가 Git에 커밋되었다는 증거는 발견하지 못했다.** 현재 로컬 환경변수 파일의 자격증명과 일치하는 값도 Git 객체·커밋 메시지 및 기존 `dist/`에서 발견되지 않았다. 이는 모든 종류의 비밀정보가 없다는 보증이나 키의 유효성 검증을 의미하지 않는다.

현재 코드에는 요청 제한 우회, 메모리 캐시 누적, 본문 크기 제한 우회가 있다. 의존성에서는 개발 도구의 알려진 취약점 1건이 2개 패키지에 걸쳐 보고되었다. 로컬 비밀파일 권한과 CSP도 보강할 필요가 있다.

## 2. 범위와 방법

- Git은 shallow clone이 아니며, 사용 가능한 전체 refs/reflog의 커밋 **101개**를 검사했다. 범위는 2026-05-11 초기 커밋부터 기준 커밋까지다.
- 도달 가능한 고유 blob **14,257개**, 총 **500,963,272바이트**를 읽었다. 이 중 텍스트로 분류한 **8,274개**에 비밀정보 패턴 검사를 적용했다. 현재 로컬 자격증명의 정확 일치 검색은 바이너리를 포함한 전체 blob에 적용했다.
- 현재 작업 트리 **248개 파일**을 검사했다. `node_modules`, `.git`, Python 가상환경·캐시 등은 작업 트리 순회에서 제외했다. `.env.local`, `tools/enrich/.env`, 미추적 `.agents/`, `.claude/`는 포함했다. 과거에 커밋된 가상환경은 Git 검사에 포함했다.
- 기존 `dist/` **2,146개 파일**에서 현재 로컬 자격증명의 정확 일치를 검사했다. 이번 점검에서 새 프로덕션 빌드를 만들지는 않았다.
- `git fsck`가 추가로 찾은 unreachable blob 1개에도 현재 자격증명 일치 여부를 확인했다.
- 자체 읽기 전용 검사로 PEM 개인키, GitHub/AWS/Google/OpenAI/Slack 형식, JWT, 인증정보가 포함된 URL, 일반적인 secret/token/password/API key 대입을 탐지했다. 발견 후보는 실제 키·예시·코드 참조로 구분했다. Gitleaks/TruffleHog는 설치되어 있지 않아 사용하지 않았다.
- `npm audit --json`, `npm audit --omit=dev --json` 및 공식 보안 권고를 확인했다.
- API를 임시 번들로 만들어 외부 `fetch`를 전부 모의 응답으로 교체한 뒤 재현했다. 실제 Redis 쓰기, GitHub Issue 생성, 운영 서버 부하 테스트, 발견한 키로 인증 시도는 하지 않았다.

작업 트리는 점검 중 다른 작업으로 변경되고 있었으므로 파일 수·재현 수치·테스트 결과는 각 검사 시점 기준이다. API 및 설정 위치는 위 기준 커밋과 대조했다.

원격 저장소의 최신 상태를 fetch하지 않았으므로 로컬에 없는 브랜치·PR·fork, GitHub Actions 로그·첨부파일, 호스팅 관리 화면·비밀변수·WAF 설정은 범위 밖이다. 인코딩·암호화·압축된 비밀값, 임의 형식의 과거 키는 패턴 검사에서 누락될 수 있다. Python 의존성 전체에 대한 CVE 감사는 수행하지 않았다.

## 4. 상세 발견 사항

### SEC-01 — 통계 요청 제한이 사용자가 바꿀 수 있는 쿠키에만 의존

**위치:** `api/stats.ts:55-62,187-204,286-313,381-386`\
**관련 커밋:** `3257864` (2026-08-25 통계 기능 도입), `95c6b04` (인기 순위), `5bdc6a9` (월별 순위)

분당 60회 제한 키는 `annical_vid`를 해시한 값으로 생성한다. 쿠키는 UUID 형식만 검사하고, 없으면 매 요청 새 UUID를 발급한다. 요청자가 쿠키를 보내지 않거나 UUID를 바꾸면 새 제한 버킷이 생긴다. 새로운 `eventId`를 보내면 중복 제거도 제한 역할을 하지 않는다.

**재현:** 동일한 모의 클라이언트가 쿠키 없이 두 번 호출했을 때 Redis 명령의 rate 키가 달라졌다. 실제 Redis 카운터 증가를 실행한 것은 아니며, 제한을 결정하는 입력과 Lua 코드를 함께 확인했다.

**영향:** 조회수·방문자 수·인기 순위 조작, Redis 호출 및 event 키 증가. 60회를 넘더라도 Lua 실행과 통계 조회는 계속 수행하므로 현재 제한은 전체 처리 비용을 차단하지 않는다.

**권고:** 신뢰할 수 있는 배포 계층의 IP·네트워크 단위 제한과 서비스 전체 쓰기 한도를 추가하고, 제한 초과 요청은 집계·조회 명령 실행 전에 종료한다. 쿠키 서명만 추가해도 쿠키 없는 요청을 통한 신규 발급은 남으므로 별도의 발급/요청 제한이 필요하다.

**완료 기준:** 쿠키 생략·변경과 새 eventId 조합으로도 정해진 클라이언트/전체 한도를 넘길 수 없고, 초과 요청이 저장소 작업을 최소화하며 거절된다.

### SEC-02 — 캘린더 캐시가 조합별 대형 응답을 계속 보관

**위치:** `api/calendar.ts:65-66,118-160`\
**관련 커밋:** `26e506a` (2026-08-22 캐시 도입), `6326f07` (그룹 필터 추가)

모듈 전역 `Map`에 정규화된 필터 조합별 ICS 전체 본문을 넣지만 항목 수·바이트 수 상한이나 퇴출 정책이 없다. 현재 카테고리 13개와 그룹 1개는 비어 있지 않은 선택 조합만 16,383개를 만든다. 전체 피드는 별도 키에 저장된다. 같은 결과를 내는 조합도 다른 키로 저장될 수 있다.

**재현:** 로컬에서 서로 다른 유효 카테고리 조합 32개만 요청했을 때 응답 본문 합계는 **13,563,917바이트**였다. 코드는 이 본문을 모두 캐시에 보관한다. 이 수치는 응답의 UTF-8 크기 합계이며 실제 JavaScript heap 측정값이나 운영 장애 재현값은 아니다.

**영향:** 동일한 재사용 인스턴스에 다양한 조합이 도달하면 메모리가 누적된다. 재시작, 캐시 미스 시 재생성 비용, 대용량 전송 비용 증가 가능성이 있다. CDN 캐시는 동일 URL에는 유효하지만 서로 다른 유효 조합을 처음 요청하는 비용을 없애지 않는다.

**권고:** 최대 항목 수와 총 바이트 예산이 있는 LRU 캐시, 과대 응답 캐시 생략, 필요한 대표 조합의 사전 생성 등을 적용한다. 만료 시간만 추가하지 말고 메모리 상한을 함께 둔다.

**완료 기준:** 상한보다 많은 유효 조합을 요청해도 캐시가 정해진 예산 안에 머무르고, 퇴출 후 재요청의 응답·ETag가 일관된다.

### SEC-03 — Vercel의 파싱된 `req.body`가 크기 검사를 건너뜀

**위치:** `api/stats.ts:207-223`, `api/feedback.ts:81-97`\
**관련 커밋:** 각각 `3257864`, `9e2eb9e`

두 `readBody` 함수 모두 `req.body !== undefined`이면 즉시 반환한다. 따라서 이후 `Content-Length` 검사와 스트림 바이트 누적 검사는 적용되지 않는다. Vercel Node.js 런타임은 JSON 요청을 파싱한 `request.body`를 제공하므로 실제 배포 방식과 관련 있는 경로다. [Vercel Node.js 요청 본문 문서](https://vercel.com/docs/functions/runtimes/node-js#request-body)

**재현:** 정상 필드에 무시되는 `padding` 필드를 추가하고 이미 파싱된 객체로 전달했다. 큰 Content-Length 헤더를 함께 주어도 아래 결과가 나왔다.

| API | 코드의 제한 | 재현 본문 크기 | 모의 외부 서비스 사용 시 응답 |
| --- | --- | --- | --- |
| `/api/stats` | 1,024바이트 | 100,109바이트 | 200 |
| `/api/feedback` | 5,000바이트 | 100,136바이트 | 201 |

**영향:** 의도한 소형 요청 제한이 무효화되어 파싱·메모리·함수 처리 비용이 증가할 수 있다. 피드백의 `message` 2,000자 제한은 별도로 남아 있다. 플랫폼 전체 요청 크기 제한이 사라지는 문제는 아니며 실제 운영 장애는 검증하지 않았다.

**권고:** 가능한 경우 자동 body helper를 끄고 원시 본문을 제한된 크기로 읽는다. 파싱된 객체를 지원해야 한다면 그 경로에도 크기·객체 형태·허용 필드 검사를 적용한다. 파싱 후 크기 검사는 후속 처리를 막을 수 있지만 이미 발생한 파싱 비용은 되돌리지 못하므로 플랫폼/진입 계층 제한도 병행한다.

**완료 기준:** 스트림과 파싱된 body 양쪽에서 제한 초과 요청이 413으로 끝나고 외부 서비스 호출은 발생하지 않는다.

### SEC-04 — 개발 의존성 Vitest의 알려진 파일 읽기 취약점

**위치:** `package.json`의 Vitest 개발 의존성, `package-lock.json:1297`의 `@vitest/mocker` 및 `node_modules/vitest` 항목\
**현재 잠금 버전:** `vitest@3.2.7`, `@vitest/mocker@3.2.7`

`npm audit` 결과는 **moderate 2개 패키지 / 고유 보안 권고 1건**이다. 대상 권고는 `GHSA-82fw-gwwq-j7x9` / `CVE-2026-84373`이며, 개발 서버의 redirect mock 경로를 이용한 파일 읽기 문제다. 공식 수정 버전에는 4.1.11이 포함된다. [Vitest 공식 보안 권고](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9)

**적용 조건:** 무인증 악용 경로는 공개 `mockerPlugin`/`interceptorPlugin`과 접근 가능한 개발 서버 WebSocket 조합이다. 현재 `vitest.config.ts`는 Node 환경이고 해당 플러그인 사용은 발견하지 못했으므로, 이 저장소의 운영 웹사이트가 곧바로 원격 파일 읽기에 노출되었다고 판단하지 않는다.

**권고:** Node·Vite 호환성을 확인한 뒤 수정된 지원 버전으로 Vitest를 올리고 잠금파일을 갱신한다. npm이 제안한 메이저 자동 수정을 검토 없이 적용하지 않는다. 개발 서버·테스트 서버의 외부 공개 여부도 확인한다.

**완료 기준:** 테스트가 통과하고 해당 권고가 audit에서 사라진다. 참고로 `npm audit --omit=dev`에서는 알려진 취약점이 **0개**였다. 이는 프로덕션 코드 전체의 안전성을 보증하지 않는다.

### SEC-05 — 로컬 자격증명 파일의 접근 권한

**위치:** `.env.local`, `tools/enrich/.env`\
**현재 상태:** 두 파일 모두 `0644`; Git 미추적 및 ignore 적용

파일 자체 권한에는 소유자 외 읽기 권한이 있다. 상위 디렉터리 접근 권한·ACL·macOS 접근 통제가 허용하는 경우 다른 로컬 계정도 내용을 읽을 수 있다. 단일 사용자 환경이나 상위 디렉터리 차단에서는 위험이 제한된다. 같은 사용자 권한으로 실행되는 악성 프로세스는 `0600`만으로 차단되지 않는다.

**권고:** 파일 권한을 `0600`으로 바꾸고, 새 비밀파일 생성 시 `umask 077`을 사용한다. 프로젝트 압축·공유·백업 시 `.gitignore`가 자동으로 보호해 주는 것은 아니므로 이 파일들이 포함되지 않도록 한다.

```sh
chmod 600 .env.local tools/enrich/.env
```

이 명령은 권고이며 이번 점검에서는 실행하지 않았다. 실제 외부 전달이나 부정 접근이 확인되면 해당 자격증명을 폐기·재발급한다.

### SEC-06 — 주요 CSP 지시문이 관찰 모드에만 있음

**위치:** `vercel.json:25-31`\
**관련 커밋:** `26e506a` (2026-08-22)

강제 CSP에는 `frame-ancestors`, `base-uri`, `object-src`, `form-action`이 있지만 `default-src`, `script-src`, `connect-src`는 Report-Only 헤더에만 있다. 해당 출처 제한은 위반을 차단하지 않는다. 설정에는 원격 보고 수집을 위한 `report-to`/`report-uri`도 없다. [MDN Report-Only 문서](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy-Report-Only)

**영향:** 별도의 스크립트 주입 결함이 생겼을 때 CSP가 스크립트 실행과 외부 통신을 제한하는 보호 효과가 부족하다. 이번 검사에서는 실제 XSS 경로를 발견하지 못했으므로 방어 보강 사항으로 분류했다.

**권고:** 분석 스크립트·웹폰트·공유 이미지 기능의 실제 출처를 확인하고 필요한 지시문을 강제 정책으로 전환한다. 호환성 확인을 위해 관찰 모드를 유지한다면 보고 수집 경로와 전환 일정을 둔다.

## 6. 오탐 방지 및 추가 확인 사항

- **피드백 IP 위조를 확정 취약점으로 분류하지 않았다.** `api/feedback.ts:107`은 X-Forwarded-For를 사용하지만 Vercel은 기본적으로 이 헤더를 덮어쓴다고 문서화한다. 다른 프록시·호스팅으로 옮길 때 신뢰 경계를 다시 검토해야 한다. [Vercel 요청 헤더 문서](https://vercel.com/docs/headers/request-headers#x-forwarded-for)
- **피드백의 `sourceUrl`은 서버가 직접 다운로드하지 않는다.** URL 입력을 받는다는 이유만으로 SSRF라고 분류하지 않았다.
- **추가 입력 검증 결함:** `api/feedback.ts:158`의 `type in TYPE_META`는 상속 속성인 `constructor`도 허용한다. 모의 재현에서 `[undefined]` 제목과 `[null]` labels가 GitHub 호출 단계까지 전달되었다. 실제 GitHub가 이를 받아 Issue를 생성한다고 검증한 것은 아니다. `Object.hasOwn(TYPE_META, type)`과 명시적 스키마 검증을 권고한다. 권한 상승·프로토타입 오염을 확인한 것은 아니다.
- GitHub App 설치 토큰 발급 요청은 권한·저장소를 추가로 축소하는 body 없이 호출한다. `.env.example`의 안내대로 설치 권한이 단일 비공개 저장소의 Issues 쓰기로 제한되어 있는지 관리 화면에서 확인할 필요가 있다. 현재 실제 설치 권한은 확인하지 못했으므로 취약점으로 단정하지 않았다.
- Python 검수기는 `build_ui().launch()`로 실행된다. 실제 외부 바인딩·공유 터널·설치 버전은 확인하지 않았다. `gradio>=4.44,<5.50` 같은 범위는 보안 패치를 보장하는 고정 버전 목록이 아니므로 실제 환경의 버전을 별도로 감사해야 한다.
