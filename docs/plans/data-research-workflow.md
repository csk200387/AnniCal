# AnniCal 데이터 추가조사 워크플로우

## 목적과 범위

기념일 수를 무작정 늘리지 않고, 생일·우리의 날에서 선택할 만한 결과와 믿을 수 있는 이야기를 늘린다. 신규 발굴과 기존 사실 재검증을 분리한다. 이번 산출물은 운영 절차·조사 템플릿·실제 데이터 기반 대기열이다. 정기 실행 자동화, 외부 자료 본조사, 서비스 데이터 수정 및 배포는 아직 하지 않았다.

## 현재 기준선 — 로컬 main 데이터 진단

| 항목 | 결과 |
|---|---:|
| 기념일 | 1,734건 |
| origin·anecdote 각각 150자 이상 | 1,734건 |
| sourceUrl 없음 | 202건 |
| sourceUrl 값은 있지만 HTTP(S) URL 형식 아님 | 30건 |
| HTTP(S) URL 형식 정상 | 1,502건 |
| 음식 카테고리 | 540건 |
| 2026년 기념일이 1개뿐인 날짜 | 10일 |
| 2026년 기념일이 2개인 날짜 | 49일 |
| 2028년 2월 29일 | 0건 |

URL 형식 정상은 링크 접속·사실 검증 완료를 뜻하지 않는다. 분량 충족도 정확성을 보증하지 않는다. 과거 문서의 숫자와 달리 지금은 글자 수를 늘리는 작업보다 출처와 날짜를 재검증하는 것이 먼저다.

발생일은 `src/utils/dateUtils.ts`의 `registerAnchors`·`resolveOccurrence`로 2026·2027·2028년 각각 계산했다. `routes.json.urlDate`로 집계하지 않았다. `annual-floating` 2건은 2026년 날짜만 저장되어 있어 2027·2028년 집계에서 빠진다. 2028년은 윤일도 별도로 조사한다.

원자료: `tools/research/workflow/baseline.json`, `source-recheck.csv`, `date-coverage.csv`. 이 자료는 구성 시점 스냅샷이며 서비스 데이터 변경 후 다시 진단해야 한다. CSV 갱신 시 진행 상태·담당자·근거 경로는 task/id 기준으로 보존한다.

## 운영 흐름

```text
현황 진단 → 조사 대기열 → 후보 발굴/기존 항목 재검증
          → 원문 근거 확보 → 중복·날짜 판정 → 한국어 편집
          → 독립 검수 → 승인 → 별도 변경 배치 → 기술 검증 → 배포 승인
```

### 상태 전이

- `queued`: 조사할 문제만 확인. 신규 기념일이 실제로 있다는 뜻이 아님.
- `researching`: 담당자 배정·조사 진행.
- `evidenced`: 날짜·적용 국가/범위·기념일 존재를 뒷받침하는 원문을 확보.
- `review`: 기존 데이터 중복 및 본문 사실·날짜 검수 중.
- `approved`: 검수자가 반영을 승인. 작성자 스스로 자동 승인하지 않는다.
- `applied`: 서비스 파일 반영 및 기술 검증 완료.
- `published`: 승인된 배포 후 실제 페이지 확인 완료.
- `blocked`: 근거 부족·출처 상충·연도 범위 문제. 필요한 추가 근거와 재검토 조건 기록.
- `rejected`: 가짜 기념일·중복·단발성 할인 행사 등. 이유를 남겨 재조사 낭비 방지.

조사 상태는 서비스 `Anniversary` 필드에 넣지 않고 조사 기록에만 저장한다.

## 우선순위

### P0 — 연도 의존 날짜와 명백한 사실 오류

2026년만 저장된 세계 수면의 날·세계 피아노의 날의 2027년 공식 일정부터 확인한다. 임의로 반복 규칙을 추정하지 않는다. 날짜·국가·제정 주체가 틀린 기존 항목을 발견하면 신규 추가보다 먼저 다룬다.

### P1 — 출처 결함과 생일 결과 부족

- 출처 문자열이 URL이 아닌 30건 → URL이 없는 202건 순으로 조사한다.
- 2026년 결과가 1개인 날짜: 02-24, 05-26, 06-16, 07-09, 07-21, 08-17, 10-07, 11-29, 12-16, 12-25.
- 2028년 02-29는 장기 결손으로 별도 조사한다.
- 같은 날의 한국·국제·문화·과학·동물·관계 소재를 우선 찾는다. 음식 540건이 있으므로 음식 목록만 추가하는 방식은 피한다.
- 목표는 우선 날짜당 검증된 선택지 3개 이상. 채우기 위해 근거가 약한 항목을 승인하지 않는다. 3개는 운영 목표이지 현재 사용자 선호를 입증한 수치가 아니다.

### P2 — 공유할 이유가 있는 새 소재

한국 맥락, 흥미로운 날짜 유래, 관계·생일 공유 문구로 쓰기 좋은 소재를 찾는다. 역사·추모·보건 항목은 사실 안내와 가벼운 유머를 구분하며 부적절한 밈을 붙이지 않는다.

### P3 — 기존 조사자료 재활용

`tools/research/jp-*.md`, `tools/namuwiki/output/`, `tools/enrich/content/`는 후보 발견에 활용한다. 과거의 '검증' 표기나 건수를 현재의 승인으로 간주하지 않는다. 현재 데이터와 다시 중복 대조하고 링크 원문을 재확인한다. 위키·블로그에서 찾았어도 가능한 경우 제정 단체 자료로 올라간다.

## 조사 실행 규칙

### 1. 작은 배치로 나누기

첫 배치는 `tools/research/workflow/first-batch.csv`의 22개 작업이다: 연도 갱신 2개, 비URL 출처 재검증 10개, 결과 1개 날짜의 신규 후보 발굴 10개. 이는 승인된 기념일 22건이 아니라 조사 과제 22개다.

신규 후보는 한 배치 10~15건을 권장한다. 날짜·지역·주제로 담당 범위를 나누고 후보 키를 공유한다. 원문 검색 결과가 없는 경우 검색어·언어·범위를 바꿔 재시도한 후 보류한다. 후보당 조사 15분을 초기 시간 상한으로 삼되, 핵심 날짜·제정 사실이 불확실하면 시간을 넘겨 단정하지 말고 blocked로 넘긴다.

### 2. 후보와 근거 수집

권장 검색 순서: 한국어/영어/현지 원어 → 기념일 원명 확정 → 공식 주최·제정 단체 → 법령·정부·국제기구 → 전문단체·신뢰 가능한 보도 → 기념일 목록·위키·블로그.

- 공식 기념일: 날짜·적용 국가·목적은 공식 자료 우선. 법정공휴일과 일반 기념일을 혼동하지 않는다.
- 비공식·브랜드 기념일: 실제 운영 주체와 반복 여부를 확인하고 비공식임을 명시한다.
- 단발성 프로모션이나 특정 해 행사 날짜를 매년 반복 기념일로 만들지 않는다.
- 제정 연도·제정 주체·날짜 이유는 각각 별개 주장이다. 대상이 탄생한 연도를 기념일 제정 연도로 바꾸지 않는다.
- 검색 요약은 발견용일 뿐이다. 본문 원문을 읽고 주장별 URL·직접 인용·접근일·원문 보관 경로를 남긴다.
- 원문 접근 실패는 '확인 완료'로 처리하지 않는다. 허용된 다른 경로나 대체 공식 출처로 확인하고 여전히 못 읽으면 blocked.
- 논쟁적·상충하는 날짜는 독립된 두 출처로 대조한다. 같은 보도자료를 재인용한 두 사이트는 독립 근거가 아니다.
- 자료 문장을 통째로 번역·복사하지 말고 근거를 바탕으로 요약한다. 인용은 검증에 필요한 짧은 범위만 보관한다.

### 3. 중복 판정

정규화한 이름만으로 자동 병합하지 않는다. 원명·별칭·기념 대상·지역·제정 주체·날짜 규칙을 함께 확인한다. 한국과 미국의 동일 명칭 기념일은 별개일 수 있다. 전세계 기념일을 번역명만 바꿔 새 항목으로 등록하지 않는다. 후보 기록에 `duplicate_of` 또는 '유사하지만 별개인 이유'를 남긴다.

### 4. 날짜 규칙 결정

`src/types/anniversary.ts`를 최종 기준으로 한다.

| dateType | 저장 형식 | 확인할 것 |
|---|---|---|
| annual-fixed | MM-DD | 정말 매년 같은 양력일인지 |
| annual-nth-weekday | MM-N-DOW | 몇째·마지막 요일이라는 공식 반복 규칙 |
| annual-relative-to-holiday | anchorId:offsetDays | anchor 존재·오프셋·순환 없음 |
| annual-tabulated | observances 표의 키 | 음력·천문 등 연도별 검증 자료 |
| annual-floating | YYYY-MM-DD | 해당 연도 공식 일정; 다음 해 자료 별도 필요 |
| one-time | YYYY-MM-DD | 반복 기념일이 아닌 1회성인지 |

최소 2026·2027·2028년 발생일을 기존 resolver로 확인한다. 도구 계산이 성공했다는 사실은 외부 일정의 정확성 근거가 아니다. 표 기반 날짜는 표 수록 범위도 기록한다. `observances.json`을 근거 없이 통째로 재생성하지 않는다.

### 5. 편집

- origin 첫 150자 안에 무슨 날인지·언제인지·어떤 범위인지가 드러나게 한다.
- origin: 제정 주체·날짜 이유·목적 중 확인된 사실.
- anecdote: 한국 맥락이나 독립적으로 확인한 이야기. 유래를 못 찾았으면 '제정 배경은 확인되지 않았다'고 기록하며 대상의 일반 역사와 기념일 유래를 구분한다.
- 기존 도구의 origin·anecdote 각각 150자 기준은 편집 점검 지표로 유지하되 자동 승인 요건으로 쓰지 않는다. 사실이 부족하면 분량을 맞추려고 내용을 지어내지 않는다.
- `memes.caption`은 사실 설명과 구별되는 편집 문구. 외부 이미지 권리가 불분명하면 text만 사용한다.
- 현재 태그 규칙은 `tags[0] = 카테고리 레이블`, 뒤에 승인된 그룹 레이블이다. 오래된 '태그 3~6개' 예시를 따르지 않는다.
- 서비스의 `sourceUrl`은 핵심 사실을 가장 잘 뒷받침하는 한 URL을 선택한다. 여러 주장에 대한 모든 근거는 조사 기록에 보존한다.

### 6. 독립 검수·승인

검수자는 원문을 다시 읽고 존재/날짜/범위/제정/본문 주장/중복을 확인한다. AI 작성 결과를 다른 AI가 읽었다는 사실만으로 사실 검증 완료라 하지 않는다. 원문과의 대조 결과를 남긴다. 사람 최종 승인 전 서비스 파일은 수정하지 않는다.

역할: 조사자(근거 수집), 편집자(한국어 본문), 검수자(원문·날짜 대조), 통합 담당(승인 배치 반영), 사용자(최종 승인·배포 승인). 병렬 작업자는 각자 배치 기록만 쓰고 월별 서비스 JSON을 동시에 편집하지 않는다.

## 승인된 배치의 반영 절차

아래는 이후 승인된 조사 결과에만 실행한다. 이번 구성 작업에서는 실행하지 않았다.

1. `git status --short`를 확인하고 기존 미커밋 변경을 보존한다. 별도 브랜치/작업 공간에서 배치별로 작업한다.
2. 기존 본문 수정은 `tools/enrich/content/<batch>.json`에 `{id: {origin, anecdote, sourceUrl}}` 형태로 작성한다. `apply.py`는 두 본문 필드를 모두 요구하므로 출처만 바꿀 때도 현행 본문을 그대로 포함해야 한다.
3. 실제 적용: `python3 tools/enrich/apply.py content/<batch>.json`. 이 도구는 즉시 월별 JSON을 쓴다. dry-run 옵션이나 승인 상태 검사 기능이 없다. 사전 승인·diff 검토가 필수다.
4. 신규 항목은 별도 승인 JSON을 준비하고 Inspector 또는 전용 검증 절차로 추가한다. Inspector 저장 역시 즉시 서비스 파일을 덮어쓴다. `apply.py`는 신규 id 추가 도구가 아니다.
5. 신규 id가 생기면 `python3 tools/slugs/generate_slugs.py`를 실행한다. 기존 id의 slug·urlDate와 REFERENCE_YEAR=2026은 보존한다. 본문/sourceUrl 수정만 있으면 재생성하지 않고 `--check`만 한다. 생성 diff에 기존 URL 변경이 있으면 중단하고 기존 매핑 보존 방식을 검토한다.
6. 새 문구는 OG 한글 폰트 커버리지에 영향을 줄 수 있다. `npm run verify`의 글리프 검사 실패 시 README의 fonttools 환경으로 `tools/og/build_fonts.py`를 실행한다. 공유 문구·폰트 변경 시 OG_VERSION·정적 PNG 갱신 필요성도 검토한다.
7. `npm run verify`를 실행하고 diff에서 승인 id 외 수정, 기존 URL 변화, tags[0] 훼손이 없는지 확인한다.
8. 신규·수정 항목의 상세/날짜 허브/생일/우리의 날/ICS/OG를 표본 확인한다. 연도 의존 항목은 다음 해 결과도 확인한다. 테스트 통과가 사실 검증을 대신하지 않는다.
9. 사용자 배포 승인 후 배포하고 정확한 대상 URL에서 본문·날짜·OG·ICS 반영을 읽어 확인한다. 실패하면 배치의 변경만 되돌린다. 원래 미커밋 변경을 지우지 않는다. 작업 중 띄운 서버·브라우저는 종료한다.

## 기록 형식과 보고

- 조사 기록: `tools/research/workflow/batches/<batch-id>/records.json` (`record-template.json`의 항목 구조 사용).
- 원문 자료: 같은 배치의 `evidence/`에 텍스트/HTML 또는 필요한 캡처. 접근 실패 상태도 남긴다.
- 검수 기록: `review.md`에 reviewer, 판정, 보류 이유, 수정 요구사항.
- 반영 배치: `tools/enrich/content/<batch-id>.json` (기존 항목) 또는 별도 신규 항목 파일.
- 완료 보고: 조사 과제 수와 후보 수를 구분한다. 후보 상태별 건수, 신규/수정 승인 수, 추가된 고유 날짜 수, 출처 결함 감소 수, 보류 사유, 기술 검증 결과를 기록한다.
- 공유율·재방문율 개선은 현재 확인된 결과가 아니다. 이벤트 측정이 갖춰진 뒤에 평가한다. 처음에는 품질과 날짜별 선택지 개선을 성과로 쓴다.

## AI 작업 지시문

> first-batch.csv에서 배정받은 task_id만 조사한다. 서비스 데이터는 읽기만 한다. 신규 발굴과 기존 재검증을 구분하고, 원문을 실제로 읽은 근거만 evidence에 기록한다. 날짜·범위·제정 연도·주체를 별개 주장으로 확인한다. 과거 조사자료와 현재 1,734건을 중복 대조한다. 기념일이 존재하지 않거나 근거를 못 찾으면 rejected/blocked로 남긴다. records.json과 review 요청 문서만 작성하고 자동 승인·적용·배포하지 않는다. 승인 가능한 건수보다 근거 정확성을 우선한다.
